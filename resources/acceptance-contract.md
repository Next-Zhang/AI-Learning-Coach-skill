# 验收、当日总结与网页清除流程契约（ticket 12）

每个学习日任务完成后的收尾流程（混合式验收，spec「混合式验收与完成度」）：**① 证据提交与核查**——学习者提交当日证据，agent 对照当日目标清单逐项核查并给结论（完成 / 部分完成 / 未完成 + 理由）；**② 完成度合成**——agent 评分与学习者自评按 7:3 合成完成度分（`scripts/completion.py`）+ 难度反馈单独采集；**③ 学习者确认**——展示结论与分数，学习者确认或质疑，确认后**验收结果写回画像**（`scripts/profile.py` `op=acceptance`）；**④ 当日总结**——写当日总结入 `progress.md`；**⑤ 网页清除**——提出删除当日网页、学习者确认后清除（approval 护栏）。

本流程依赖既有脚本（ticket 04/05/06）：`scripts/completion.py`（完成度合成，契约见 `resources/completion-contract.md`）、`scripts/profile.py`（`op=acceptance` 写回能力矩阵，契约见 `resources/profile-contract.md`）。这些脚本的输入输出格式各自见对应契约，本文档**不重复其格式**，只规定验收收尾的**对话编排**如何调用它们，与各 ticket 的越界分工。`progress.md` 的格式约定见 `resources/data-formats.md` §2。

按 spec「测试 seam」：对话式流程（计划生成、验收对话等）**不设自动化 seam**，构建后通过**实际演练验证**；本文档定义对话协议本身。

---

## 1. 目标与范围

- **目的**：把"今日任务完成"变成一次**双方共识的验收**——学习者先自证（证据），agent 对照当日目标核查给结论，完成度由「agent 评分 70% + 自评 30%」合成且**最终判定权在学习者**（可质疑、可拒认）；确认后才把当日总结写入 `progress.md`、把验收结果写回能力矩阵，最后清理当日临时网页。结论、分数、总结都落到学习者本人的确认上，避免"自报打卡"或"AI 独断"两个极端（spec「混合式验收」）。
- **范围**：只做当日收尾这些事——证据核查与结论、完成度合成与难度采集、学习者确认、验收结果写回画像、当日总结写入 `progress.md`、网页删除。复习快查文档生成与调度表 `add` 属 ticket 13，会话开头的复习/网页生成属 ticket 11，**本流程不越界**。
- **硬约束**：核查必须对照 `plan.md` 当日目标清单逐项进行，结论与理由透明且基于证据；完成度合成必须走 `scripts/completion.py`（7:3、0.5 档）并展示算式；难度反馈独立采集、独立记录、**不参与完成度分**；任何持久层写入（`profile.md` 写回、`progress.md` 追加）与网页删除都先经学习者确认（护栏 approval）；引用规范：总结与核查理由里的事实不编造，涉及当日知识点的关键事实引用当日来源。

## 2. 起点与前置

- **前置**：本日会话已走完「会话开始」（ticket 11）与当日执行辅助，当日任务收尾（ticket 11 `session-start-contract.md` §7 收尾）→ 进入本流程；`plan.md`（`status: active`，含当日 Day 区块）与当日执行网页已在本会话生成。
- **读取**（进入时只读）：`plan.md` 当日 Day 区块（主题 / 目标清单 / 知识点 / 来源）、本会话生成的当日网页路径（`page.py` 输出 JSON 的 `html_path`，会话内已知）、`profile.md` 能力矩阵（写回基准，`updated` 会在写回时更新）。
- **开场示例**："今天的内容到这儿了。开始验收——把你今天的成果贴给我：写过的代码、跑出来的结果、或者你的回答。我对照今天的 3 项目标逐条核对，然后我们各自打分，合成今天的完成度。"
- **分支**（核查中发现异常时）：证据不足以判断某项 → 请学习者补充（贴关键代码/运行输出截图文字）；当日任务明显没做 → 如实记「未完成」，不催不逼，验收照常走（分数低、总结如实记录），任务顺延的沟通放在总结之后。

## 3. 证据提交与核查

### 3.1 证据提交

- 学习者贴当日证据：代码片段、运行结果（输出/文件）、回答、或实操描述。位置不限，格式不限（对话内贴文即可），**证据只在本会话使用，不写进持久层**（`progress.md` 只留摘要，见 §7）。
- 证据不足时先补证再核查，不进下一步。

### 3.2 逐项目标核查

对照 `plan.md` 当日目标清单（`- [ ]` 条）**逐条**核对，证据 → 目标 一一映射：

- 每条目标给出：**判定（达成 / 部分达成 / 未达成）+ 依据**（引用证据里哪段代码/哪个运行结果）；
- 达成 = 证据表明该动作正确完成且理解正确（含在教练纠错引导下已改对——纠错是辅助不是代做，改对即算达成，但**过程依赖纠错这一事实计入评分理由**）；
- 未达成 = 没做、做错且未修正、或证据无法支撑。

### 3.3 结论与理由

逐条核查后给出**当日结论**：

| 结论 | 判定标准（目标清单达成情况） |
| --- | --- |
| 完成 | 全部目标达成（或教练纠错后达成） |
| 部分完成 | 有达成也有未达成 / 部分达成 |
| 未完成 | 全部或多数目标未达成 |

- 结论必须带理由：列出「逐条判定表」（目标 → 达成与否 → 证据依据），并总结为 1–3 句结论说明（如"3 项目标全达成，但读取筛选中链式索引赋值是教练纠错后改对"）。
- 结论是**教学质量约束**：只评证据与当日目标，不横向比较、不评价人格；未达成的目标如实指出差距，不粉饰。

## 4. 完成度合成 + 难度反馈采集

1. **agent 评分**（1–5）：基于逐条核查结论 + 证据质量与过程（含依赖纠错的程度）给分；结论与分数的大致对应（供一致性参考，**分数还包含过程质量，不机械绑定结论**）：
   - 完成 → 4–5 分；
   - 部分完成 → 3–3.5 分；
   - 未完成 → 1–2.5 分。
2. **学习者自评**（1–5）：请学习者给自己的今日表现打分，**先各自独立给**（先不让学习者看见 agent 分再改）。
3. **合成**：调 `scripts/completion.py`，输入 `agent_score` / `self_score` / `difficulty` → 输出 `raw` / `score` / `score_display` / `synthesis` / `difficulty`；把算式与完成度展示给学习者：
   - 如输出 `{"agent_score": 4, "self_score": 5, "raw": 4.3, "score": 4.5, "score_display": "4.5/5", "synthesis": "0.7 × 4 + 0.3 × 5 ≈ 4.5", "difficulty": "太难"}` → 展示："合成完成度 4.5/5（0.7 × 4 + 0.3 × 5 ≈ 4.5）。请确认，或告诉我哪里不对。"
   - 合成规则与 0.5 档取整见 `resources/completion-contract.md` §4；**不口算代替脚本**。
4. **难度反馈采集**：确认完成度后，单独问一句今日难度（`太难` / `刚好` / `太简单`，学习者可说明理由）。语义重申：**不参与完成度分**，只记录并在后续计划难度档位参考（spec「完成度评分」）。

## 5. 学习者确认环节

- 展示一张**验收单**：结论 + 逐条判定表 + 完成度（算式）+ 难度反馈，请学习者**确认或质疑**。最终判定权在学习者（spec「混合式验收」）。
- **质疑处理**（学习者对结论、得分、判定依据有异议）：
  - 逐条复核证据与目标（重新对照证据，不预设结论）；
  - 复核后有据 → 修正判定 / 调整 agent 评分 → 重跑 `scripts/completion.py`（新输入）→ 重新展示确认；
  - 复核后无据 → 维持原判定，并解释依据，**尊重学习者的最终确认权**：学习者在理解依据后仍可坚持其自评分（自评分本就是学习者的）。
  - 说明原则："难度是独立记录、独立反馈，不因为今天难或环境坑而扣完成度；反之也不因为全做出来就一定 5 分——分数含过程质量与独立完成度。"（学习者常混淆这两点，须明确一次。）
- **确认后才可继续**（§6/§7/§8 的所有写入都基于这份确认）；学习者要求中止 → 本日验收搁置，**不写任何持久层**（不写半成品），数据保持验收前状态，下次会话可重新验收（新会话按同样契约走）。

## 6. 验收结果写回（profile.py op=acceptance）

1. **写回清单**：当日任务「知识点」字段的**每个**知识点各写回一次（同完成度、同难度；当日多知识点共用当日一个完成度分）。展示清单：知识点 → 当前水平分 → 将如何变化（完成度 ≥ 4 → +0.5，上限 5；< 4 → 不变，仅记日志）→ 难度反馈入增量日志。
2. **确认后逐一调用** `scripts/profile.py`，`op=acceptance`，`topic`（当日知识点）、`score`（合成完成度分）、`difficulty`（§4 采集值，可选）、`source`（建议 `「验收 Day N」`，契约 `resources/profile-contract.md` §2）→ 输出 `old_score` / `new_score` / `delta` / `log_entry`。
3. **汇报**：汇总写回结果（如"Excel 读写 3 → 3.5 +0.5，难度「太难」已记入画像，不影响本次完成度"）。能力矩阵是权威值（`resources/data-formats.md` §3）。
4. **approval 护栏**：本步原地改写 `profile.md`（矩阵行 + 增量记录 + frontmatter `updated`），属持久层修改，**先展示写回清单、经学习者确认后执行**；同一验收批的多个知识点一次批量确认，不逐条打扰。

## 7. 当日总结写入 progress.md

1. **起草总结块**（格式遵循 `resources/data-formats.md` §2，结构与示例完全一致）：

   ```markdown
   ## 2026-08-25 — Day 5
   - 当日任务：Excel 读写（读取与列筛选）
   - 完成度：4.5/5（0.7 × 4 + 0.3 × 5 ≈ 4.5）
   - 难度反馈：太难
   - 当日总结：学会了 read_excel / to_excel 与 sheet_name 指定工作表，完成「读入 → 筛选 → 写出」小程序；卡点：openpyxl 缺失（环境坑）与链式索引赋值（已用 loc 修正）。总评：目标 3/3 达成……
   - 证据摘要：read_excel('报表.xlsx') + sheet_name='明细' 成功读出；df.loc[df['金额'] > 100, '金额'] = 0 做筛选；to_excel('结果.xlsx') 写出文件确认
   ```

   - 「完成度」写 `score_display`，可附合成算式（照抄脚本 `synthesis`）；
   - 「难度反馈」独立行，`太难 | 刚好 | 太简单`；
   - 「当日总结」由 agent 依据 §3 结论与逐条判定撰写（学到什么、卡点与解决、下一步关注点——基于证据与当日内容，关键事实引用当日来源，**不新增无依据断言**）；
   - 「证据摘要」只留要点与位置，不贴整段代码（正文可引述关键几行，spec 与 `data-formats.md` §2 约定）。
2. **展示 → 确认**：把写好的总结块展示给学习者，确认后**追加**到 `progress.md` 文件末尾（最新一天在最后）并更新 frontmatter `updated` = 今天。**追加语义**：只尾加，不改既往日期的任何内容。
3. **approval 护栏**：`progress.md` 属持久层六件套，写前先经学习者确认（护栏 approval）；**不确认不写**，此时画像写回与进度写入都不发生（保持验收前状态）。

## 8. 网页清除

1. **时机**：当日总结写入完成之后、收尾之前。
2. **提出删除**：说明清楚删什么、为什么删、删了会怎样——"今天的执行网页是临时文件（`day-5-2026-08-25.html`），验收与总结都已完成，我建议把它删掉，页面不累积。模板留在技能里，明天会为新的一天重新生成。"**不得静默删除**。
3. **确认后删除**：学习者明确同意后删除该 HTML 文件（approval 护栏，删除需显式批准，见 SKILL.md「护栏」）。
4. **学习者拒绝**：尊重选择，保留网页（它只是临时文件，不影响持久层与后续会话）；可提示可自行删除或留待参考。
5. **收尾汇报**：删除后一句话汇报当日闭环（"Day 5 验收完成：完成度 4.5/5，总结已写入进度，当日网页已删除。明天见。"）并提示明日新会话。

## 9. 边界与护栏

- **ticket 分工**：不生成复习快查文档、不更新调度表 `add`/`record`（ticket 13）；不做会话开头的事（复习考察、网页生成，ticket 11）；`progress.md` 只写当日总结块、不重构历史。
- **approval**（全部写入前确认）：
  - `profile.md` 写回（§6）：展示写回清单、批量一次确认；
  - `progress.md` 追加（§7）：展示总结块、确认后写；
  - 网页删除（§8）：显式提出、明确同意后删。
  - **任何一步未确认 → 不执行**；学习者中止 → 全部保持验收前状态、下个会话按本契约重走。
- **完成度与难度分离**：难度反馈独立采集、独立记录，不参与完成度分（`completion.py` 与 `profile.py` 语义一致）。
- **引用规范**：核查理由、总结内容基于当日证据与当日来源；关键事实引用来源，不编造、不把新知识点断言写进总结。
- **防空转**：证据补证最多 1 次追问；质疑复核轮次上限 3 轮（超限以学习者最终确认意见为准并记录分歧）；总结起草一次过、只按学习者意见小改；整体会话遵守 30 步上限（护栏「运行参数上限」）。

## 10. 验证方式

- 本流程为对话式流程，按 spec「测试 seam」**不设自动化 seam**，构建后通过**实际演练验证**。演练产物存于 `.scratch/python-coach/rehearsal-12/`。
- **演练记录（2026-08-25，ticket 12 构建时，Day 5 晚间场景）**：前置数据延续 rehearsal-11 的 Day 5 早晨产物（`data/` 工作数据 + 当日网页），并补 Day 1–4 进度（`progress.md`）；走通「证据提交 → 逐项目标核查（3/3 达成）→ 结论『完成』→ agent 4 / 自评 5 → `completion.py` 合成 4.5/5（0.7×4+0.3×5≈4.5）→ 学习者就评分与难度语义提出质疑 → agent 复核维持（难度不参与完成度、loc 纠错计入评分理由）→ 确认 4.5/5 → 难度采集『太难』→ 最终验收单确认 → `profile.py op=acceptance`（Excel 读写 3→3.5）→ 总结块确认 → 追加 `progress.md` → 提出删除当日网页 → 学习者确认 → 删除」。详细转写与脚本记录见 `rehearsal-12/rehearsal-log.md`。
- 量化逻辑的自动化测试另由 `scripts/test_completion.py`（ticket 04）与 `scripts/test_profile.py`（ticket 05）兜底；`progress.md` 格式自检由本演练 + `resources/data-formats.md` §2 保证。
