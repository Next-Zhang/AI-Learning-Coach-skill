# 计划生成与三验证流程契约（ticket 10）

起步流程第 4 步：基于已确认的**目标 + 范围声明 + 能力矩阵**，生成**按天划分、含来源引用**的计划草案 → 落盘前起**独立评审 agent** 做三验证（真实性：逐项对照检索来源；合理性：主题顺序/深度/份量；适配性：对照画像）→ 评审问题清单 → 修订 → 再评审 → **全部通过才落盘 `plan.md`（`status: active`）**。

按 spec「测试 seam」：对话式流程（计划生成、验收对话等）**不设自动化 seam**，构建后通过实际演练验证；本文档定义对话协议本身（含多 agent 评审协议）。写入的 `plan.md` 格式遵循 `resources/data-formats.md` §1 且必须能被 `scripts/page.py` 解析（解析规则见 `resources/page-contract.md` §5，`scripts/test_page.py` 有 plan.md 解析测试），本文档不再重复数据格式，只规定如何生成、评审、修订并落盘。

---

## 1. 目标与范围

- **目的**：把 ticket 08 确定的目标与范围 + ticket 09 的能力矩阵，编排成一条按天执行的学习计划（每日主题、目标清单、知识点、来源引用），经独立评审 agent 三验证后才成为生效计划（`status: active`）——让学习者确信"计划有可靠来源、顺序与份量教学上成立、贴合我这个人"。
- **范围**：只做计划草案生成 + 三验证 + 修订循环 + 落盘。每日执行/网页生成属 ticket 11、验收/总结属 ticket 12、复习沉淀属 ticket 13，**本流程不越界**。
- **硬约束**：计划内容只出自 `scope_covered`（`scope_excluded` 不得进入主题序列）；**每条计划项带来源引用**；未通过三验证不落盘；评审 agent 必须与主会话隔离；评审轮次上限 3（护栏「运行参数上限」）；写入 `plan.md` 属持久层修改，执行前先经学习者确认（护栏 approval）。

## 2. 起点与前置

- **前置**：`plan.md` 草案已落盘（ticket 08，`status: draft`）、`profile.md` 能力矩阵已建立（ticket 09，来源「摸底测试」）、`sources/` 资料库与检索层脚本就位（ticket 02）。
- **输入**（本流程开始时逐一读取）：
  1. `plan.md` frontmatter：`goal`、`scope_covered`、`scope_excluded`、`created`；
  2. `profile.md`：onboarding 8 题（尤其 Python 水平自评、每日时间预算、期望节奏、压力自评、学习风格偏好）+ 能力矩阵（知识点 × 水平分 × 来源日期）；
  3. `sources/` 目录与检索层脚本 `scripts/retrieve.py`。
- **开场示例**："目标『用 Python 处理 Excel 报表并做数据分析』和范围（覆盖：语法基础、数据分析（pandas）、Excel 处理、数据可视化；不涉及：Web 框架、网络爬虫）都已确认，摸底矩阵也建好了。现在我来排一个按天执行的计划草案，排好后请一个与本次对话隔离的独立评审员检查三件事：内容是否都有可靠来源、顺序与每天的量是否合理、是否贴合你的画像。全部通过才会落盘。"

## 3. 计划草案生成（按天划分、含来源引用）

### 3.1 天数与份量估算（对齐画像）

按如下规则估算总学习天数 `T`，**展示规则推导过程**并请学习者确认（学习者可上调/下调天数或每日份量，但不改主题顺序与范围；要改范围须回 ticket 08）：

1. 划分知识点归属：把能力矩阵每行映射到 `scope_covered` 的一个子领域。每个子领域 `s` 取均值 `m_s`（矩阵分均值，0.5 档）；子领域内无矩阵行时按画像「Python 水平自评」折算 `min(自评, 3)`。
2. 子领域日需求 `d_s`：
   - `m_s ≤ 1.5` → 2.0 天（低水平，需铺垫 + 多轮练习）
   - `1.5 < m_s ≤ 3.0` → 1.5 天
   - `m_s > 3.0` → 1.0 天（快过）
   实际排天时每天为整数天，故每个子领域占用 `ceil(d_s)` 天。
3. `T0 = Σ ceil(d_s)`，再按画像微调：
   - 每日时间预算 ≤ 30 分钟 → `T = ceil(T0 × 1.25)`（每天只排 1 个知识点，份量减半）
   - ≥ 2 小时/天 → `T = ceil(T0 × 0.8)`（每天可容纳 1–2 知识点 + 1 个练习）
   - 期望节奏「快」→ `T = ceil(T × 0.85)`；「平缓」不变；「慢」→ `T = ceil(T × 1.15)`
   - 压力自评 ≥ 4：不排冲刺式安排（相邻天不连续放大份量）
   - 截断到 `[7, 30]` 天。
4. 若目标指向"产出"型（如"做一份报表分析"），可在尾部加 **1 天综合实战**：只复用已覆盖知识点、不引入新知识点，把前面所学串成目标产出。

### 3.2 主题顺序编排（前置 → 核心 → 扩展）

- 大序：前置子领域 → 目标核心子领域 → 扩展子领域。同子领域内知识点按**依赖序**排列（语法基础先于 pandas、基础绘图先于图表定制、数据读取先于数据清洗）。
- 相邻天主题尽量连续、不来回跳领域（教学连贯性）。
- 严禁把有依赖关系的知识点顺序倒置（合理性评审的检查重点）。

### 3.3 逐日拆解与来源引用

每天一个任务单元，字段与 `resources/data-formats.md` §1 完全一致：

- `主题`：当日一句主题（比知识点更口语，如「pandas Series 与 DataFrame 入门」）。
- `目标清单`：2–4 条、动词开头、可勾选、当日可完成的动作（对齐当日主题与知识点；**绝不写范围外目标**）。
- `知识点`：与能力矩阵粒度一致的知识点名（如 `pandas.Series`），逗号分隔。
- `来源`：当日主题/知识点的依据来源——**先对每日主题与知识点逐一跑检索层**（`scripts/retrieve.py`，query 用知识点名词；本地**相关**命中——与当日主题/知识点实质对应的命中，非仅关键词沾边——不足 3 条时允许一次 web 补充，契约见 `resources/retrieval-contract.md` §5，阈值以相关性显式设定），从返回命中中引用 `sources/x.md` 或 URL；**无命中的断言不得入草案**（护栏「引用规范」）。

> **存档检索记录**：每个查询的 query、limit、命中列表（标题/来源/摘要）连同该日引用一起存档；**凡使用了 web 补充的日子，须在检索记录里写明相关性判断依据**（本地命中哪些、为何判定相关命中不足），作为真实性评审的核对手册（§4 评审输入的一部分）。

### 3.4 草案展示与学习者确认

- 展示：总天数与推导理由 → 主题序列一览 → 每日明细（主题/目标/知识点/来源）→ 请学习者确认草案的结构与份量。"这一步只确认结构；内容的三重审查交给独立评审员。"
- 学习者可要求：加/减天数、调整每日份量（知识密度）、换主题措辞与目标清单表述——不动范围与依赖顺序（要改依赖顺序须明说理由，评审仍会复查）。

## 4. 三验证（独立评审 agent）

### 4.1 独立性要求

- 评审 agent 必须与主会话**隔离**：用 harness 的子代理能力起一个**全新会话**的评审 agent，不带本会话对话上下文；评审 agent 只读评审包裹、不与学习者对话、输出完即结束。
- 评审 agent 看不到学习者的作答过程，也不得接触本会话其他材料；判断只基于打包给它的材料。
- 主 agent 不得替评审 agent 作答、不得在打包前预设结论；三轮次的三份评审各自独立。

### 4.2 评审输入打包

主 agent 把评审输入打包为**单个 Markdown 文件**（评审包裹），包含：

1. 学习目标（goal）；
2. 范围声明（scope_covered / scope_excluded）；
3. 画像摘要：Python 水平自评、每日时间预算、期望节奏、压力自评、学习风格偏好 + 完整能力矩阵表；
4. 计划草案全文（所有 Day 区块）；
5. 检索记录：每个主题/知识点的检索 query、命中列表（标题/来源/摘要/链接），以及是否使用了 web 补充。

打包后经 harness 子代理工具把**文件路径传给独立评审 agent**，指示它只读这份材料、输出三份结构化评审。评审包裹文件放工作目录临时区（演练时为 `rehearsal-10/review/`），非持久六件套。

### 4.3 三份评审的输出结构与判定标准

评审 agent 输出**三份评审**（真实性 / 合理性 / 适配性），每份格式：

```
结论：通过 | 有问题
问题清单（无则留空）每项一行：`[编号] 级别（阻塞|建议）| 对应计划项 | 描述 | 建议修订`
```

- **真实性审核**：逐项对照检索记录——每个目标清单条目、知识点、主题断言都必须在对应检索命中里有依据（摘要或来源）。判定：计划项引用的来源不在检索命中中、或断言无任何检索依据 → **阻塞**；引用与检索记录不一致（引了没查过的来源、导向错误的来源）→ **阻塞**；全部有依据 → 通过。
- **合理性审核**：主题顺序（先决依赖是否倒置、跨天是否跳领域）、深度（相对矩阵分：低分子领域是否配了足够铺垫、高分子领域是否还在重复低水平内容）、份量（相对每日时间预算：如 1 小时/天塞 3 个知识点 → 阻塞；每日份量忽大忽小、冲刺式安排 → 阻塞）。教学硬伤（顺序倒置、明显超量）→ 阻塞，其余为建议。
- **适配性审核**：对照画像逐维核对——目标（计划是否真的通向『处理 Excel 报表并做数据分析』）、水平自评与矩阵（起点深度是否匹配，如新手是否从语法基础起步）、时间预算（总投入 = 总天数 × 每日份量，是否匹配）、期望节奏（快/慢）、压力自评（低压力者不排高强度天）、风格偏好（题量比例是否照顾『动手练习』偏好）。不匹配 → 阻塞或建议，给出调整方向。

评审 agent 还须**交叉检查边界**：是否遗漏某个 `scope_covered` 子领域、是否夹带 `scope_excluded` 内容（发现即阻塞）。

问题编号全计划唯一（如 `R1` 合理性、`Z2` 真实性、`S3` 适配性…），级别 = `阻塞 | 建议`。

## 5. 评审 → 修订 → 再评审循环

1. 主 agent 收集三份评审（一轮评审只起一个评审 agent，三份评审一次返回）。
2. 三份全「通过」→ 进入落盘（§6）。
3. 否则主 agent **修订草案**：只改被指出问题的对应项，**不引入新主题、不回退已通过的项**；修订说明记录在评审留档里（改了哪几项、为什么）。
4. 修订稿连同上一轮问题清单再打包，起**新的独立评审 agent**（全新会话）完整重审，要求它先确认上一轮问题逐条解决情况，再检查新引入的内容。
5. 重复直至通过或达上限。**评审轮次上限 3 轮**（护栏「运行参数上限」）。
6. 第 3 轮仍未全部通过 → **停止并降级**：不落盘 `active`，把问题清单与当前草案存档，向学习者说明卡点（哪些项没过、为什么），请学习者选择：调整输入（改目标/范围/期望天数）重走本流程，或放弃本次生成。**不写半成品 plan.md**。

> `plan.md` 保持 `draft` 直到通过验证；验证期间学习者可随时提出调整（改天数、改措辞），每次输入变化后轮次计数重置（评审对象变了）。

## 6. 落盘 plan.md（status: active）

1. **展示终稿**：计划全文（天数/主题序列/每日明细）+ 三份评审结论摘要（每份「通过」+ 一到两句），请学习者确认后写入。
2. **写入** `plan.md`：以草案为基础，frontmatter `status: active`、`updated` = 今天，正文保留全部 Day 区块（字段与解析规则以 `resources/data-formats.md` §1 与 `resources/page-contract.md` §5 为唯一权威，本契约不重复）。
3. **格式自检**：调用 `scripts/page.py` 以 `plan.md` 为 `plan_path` 跑一次（任取一日）确认可正常解析（拿到当日任务各字段、HTML 生成成功）；脚本只读不写持久层。ticket 11 起每日网页生成依赖此格式。
4. **approval 护栏**：`plan.md` 属持久层六件套，落盘/覆盖前先经学习者确认（SKILL.md 护栏 approval）。
5. **覆盖语义**：`plan.md` 已有生效计划（学习者重走起步）→ 先说明将覆盖每日任务并置回 `active`（旧任务被替换；进度保留在 `progress.md`，不受影响），学习者确认后才写；仅改写任务清单与 `status`/`updated`，`goal`/`scope` 由 ticket 08 重走时决定。
6. 落盘后简述：计划已生效、共 N 天，从 Day 1 开始；进入「会话开始」第 2 步（复习检查 → 当日执行）。

## 7. 边界与护栏

- 不越过本流程：不生成每日网页（ticket 11）、不写 progress（ticket 12）、不生成复习快查或调度表（ticket 13）、不新增/改写 `sources/` 资料。
- 计划内容只出自 `scope_covered`；禁止夹带 `scope_excluded` 内容。
- 无来源断言的计划项禁止进入草案与落盘（护栏「引用规范」）。
- 评审 agent 独立性：全新会话、只读打包材料、不与学习者交互；主 agent 不预设结论。
- 评审轮次上限 3 轮；每轮必有输出（通过或问题清单），无空转。
- 中途退出：不写半成品 `plan.md`；验证未通过不落盘，草案与问题清单留档供下次重走。

## 8. 验证方式

- 本流程为对话式 + 多 agent 流程，按 spec「测试 seam」**不设自动化 seam**，构建后通过**实际演练**验证。
- **演练记录（2026-08-21，ticket 10 构建时，用真实独立子代理跑评审轮）**：完整链路「草案 → 评审轮 1 → 修订 → 评审轮 2 → 落盘」走通。起点：`goal`「用 Python 处理 Excel 报表并做数据分析」、`scope_covered` 四子领域、能力矩阵 10 知识点（来自演练 08/09 数据）。天数推导：语法基础 1.17 → 2 天、pandas 1.67 → 2 天、Excel 处理 2.25 → 2 天、数据可视化 2.75 → 2 天 = 8 天内容 + 产出型 1 天综合实战 = 9 天（工作日 1h/周末 2h、平缓、压力 3，无调整触发）。每主题/知识点跑检索层 `retrieve.py` 并**存档检索记录**（`rehearsal-10/retrieval-log.md`，本地相关命中不足 3 条时 web 补充并入，web 结果含真实视频链接）。
  - **评审轮 1（独立 subagent 三验证）**：真实性/合理性/边界交叉检查通过；**适配性有问题 1 条**：[S-1]（建议）画像偏好「视频 + 动手练习」但全计划 0 视频来源——另外合理性 2 条建议（[R-1] Day 7 工作日在 1h 内同时安排折线+柱状、figure/axes 概念与 2 练习偏紧；[R-2] Day 5「读入→简单处理→写出」先于 Day 6 清洗顺序略反直觉）。
  - **修订（只改被指出项）**：S-1 → 各 Day（Day 1–8）来源补充视频链接（均从检索命中获取）；R-1 → figure/axes 降为「了解即可」并收敛目标；R-2 → Day 5 主题与小程序目标注明「清洗在 Day 6 引入、仅筛选」。修订记录 `rehearsal-10/revision-log.md`。
  - **评审轮 2（新的独立 subagent 完整重审）**：三份全部「通过」、问题清单为空；上一轮 3 项问题逐条确认解决、未引入新问题（新增视频逐日核验都在对应 Day 命中内）。→ 落盘。
  - **落盘**：`rehearsal-10/plan.md` 置 `status: active`、每日任务齐备 → `scripts/page.py` 按全部 9 天逐一自检通过（汇总见 `rehearsal-10/page-check-all.json`：9 天全部解析、每日字段与来源正确拆分）。
  - 产物：`rehearsal-10/`（画像/资料副本、检索记录、`plan.draft-1.md`、`plan.draft-2.md`、修订记录、终稿 `plan.md`、`page-check-all.json`）；`review/`（in-1/out-1/in-2/out-2）。
- 演练产物存于 `.scratch/python-coach/rehearsal-10/`：画像副本、资料副本（`sources/`）、草案（`plan.draft-*.md`）、检索记录（`retrieval-log.md`）、评审包裹（`review/in-*.md`）、评审输出（`review/out-*.md`）、修订记录（`revision-log.md`）、终稿（`plan.md`）。
- 终稿格式兼容性另有 `scripts/test_page.py` 的 plan.md 解析测试兜底（`resources/page-contract.md` §6）。
